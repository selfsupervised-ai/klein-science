  <action>
Build the golden protocol end to end on the smoke programs (per D-10, D-01; CONF-01).

1. Add `OracleCmd::Golden` with these options:
   - `name` (the manifest stem);
   - `input` (a path or sha256);
   - `seeds` (default 0,1,2,4294967295);
   - `runs` (default 2);
   - `platforms` (default linux/arm64,linux/amd64);
   - `jobs`, `cpu_seconds` (default 60);
   - `verify <manifest path>`.
2. Golden run:
   - ensure the sympy image for each platform matches the pin, loading it with `--from-store` if needed;
   - for each platform, seed and run, call the existing run path with `--require-sympy-env` and the run_programs script, and collect the canonical records digest;
   - load all run blobs from the store and group the lines by case_id;
   - a case is golden only if its canonical record bytes are identical in every run. Otherwise it becomes an adjudication entry `{case_id, reason}`. The reason is "status" if the statuses differ, else "platform" if the records differ between platforms, else "seed" if they differ between seeds on one platform, else "run";
   - write the golden JSONL (agreeing records, sorted by case_id) and `store put` it.
3. The manifest is written as JCS through ksci_wire::to_jcs, to a temp file that is renamed only after every run has completed. Its keys:
   - name;
   - input_sha256;
   - images: the sympy identity and tar sha256 per platform, plus whether the platform was emulated (amd64 on the Mac);
   - run_programs_blob: the output of `git hash-object conformance/oracles/run_programs.py`;
   - params: seeds, runs, platforms, cpu_seconds, mem_bytes, jobs;
   - runs: a list of `{platform, seed, run, records_sha256}` in a fixed order;
   - counts: cases, golden, adjudication, and golden counts by status;
   - golden_sha256;
   - adjudication: sorted by case_id.
4. `--verify <manifest>` reloads the run blobs named in the manifest, recomputes everything except the container runs, and fails unless the regenerated manifest bytes equal the file's bytes.
5. Run `cargo xtask oracle golden --name smoke-v1 --input testdata/programs/smoke.jsonl --cpu-seconds 2`.
   - Expected: the set-printing case is in adjudication with reason "seed". The deterministic ok and error cases are golden. The CPU and wall timeout cases are either golden with status timeout in all 16 runs or adjudicated with reason "status"; record which.
   - Then run `cargo xtask oracle golden --verify conformance/golden/smoke-v1.golden.json`.
   - Record the seed-sensitive quarantine as the RED witness of the reproducibility check in the SUMMARY.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| oracle runs → goldens | Goldens become the truth every later phase is scored against |
| store → verify | Run blobs are re-read from the store to re-derive the manifest |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-27 | Tampering (flaky truth) | golden admission | high | mitigate | A case is admitted only with identical canonical bytes across 16 runs (4 seeds × 2 runs × 2 platforms). Disagreements are quarantined with a reason. The seed-sensitive witness was seen RED. |
| T-01-28 | Tampering | golden bytes at rest | medium | mitigate | Golden and run blobs are addressed by sha256 and re-hashed on every fetch. `--verify` re-derives the manifest from the run blobs and must match byte for byte. The manifest is in git. |
| T-01-SC | Tampering | images used | low | mitigate | Only the pinned sympy image identities from images.json, verified before each run. No new package installs. |
</threat_model>
